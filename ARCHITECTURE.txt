Chap Project Structure
======================

## 앱 소개

Chap — 키보드 단축키 한 번으로 웹사이트·앱·폴더를 원하는 화면, 원하는 크기로 즉시 여는 macOS 메뉴바 런처.

## 데이터 모델

Site 모델 필드:
  - name: String              사이트 이름
  - url: String               URL (launchType=url일 때 사용)
  - width: Int                윈도우 너비
  - height: Int               윈도우 높이
  - displayName: String?      대상 디스플레이 이름. UI 표시 + 폴백 매칭용
  - displayIdentifier: String? 대상 디스플레이 UUID(CGDisplay). 매칭 우선순위 1순위.
                              동일 모델 외장 모니터가 여러 대여도 물리 디스플레이별로 달라 정확히 구분됨.
                              nil이면(구버전 config/Follow Cursor) displayName으로 폴백.
                              displayName/displayIdentifier가 둘 다 nil이면 Follow Cursor(커서 화면)
  - windowSizePreset: String? 프리셋 ID (Follow Cursor면 내장 화면 기준, 지정 화면이면 대상 화면 기준, nil이면 Custom)
  - displaySizeOverrides: [DisplaySizeOverride] 화면별 size/preset override. 실제 실행 화면과
                              UUID → unique displayName 순으로 매칭되면 기본 size보다 우선 적용
  - launchType: LaunchType    url | app | finder | shell
  - reuseExistingWindow: Bool URL 타입에서 현재 세션에 연결된 Chap 생성 Chrome 창 재사용 여부. 누락 시 false
  - appPath: String?          앱 경로 (launchType=app)
  - script: String?           스크립트 내용 (launchType=shell)
  - folderPath: String?       폴더 경로 (launchType=finder)
  - shortcut: String?         커스텀 단축키 ("T" → ⌥T)

Config 모델 필드:
  - showGuideWindow: Bool     리사이즈 위치 가이드 윈도우 표시 여부
  - launchAtLogin: Bool       로그인 시 자동 실행
  - optionShortcutsEnabled: Bool  Option 글로벌 단축키 활성 여부. 누락 시 true
  - statusBarIcon: StatusBarIconChoice  상태바 아이콘 ("default" | "lightning"). 누락 시 "default"
  - sites: [Site]             사이트 목록

※ 윈도우 위치(x, y)는 저장하지 않음 — 항상 대상 화면 중앙에 자동 배치.


## 핵심 기능

- Settings > General의 Enable Chap Option-Key Triggers 토글로 글로벌 단축키
  (⌥., ⌥커스텀키, ⌥,) 전체 on/off. 활성화 시 RegisterEventHotKey로 정확한 조합만 시스템 등록
  (일반 키 입력은 Chap을 거치지 않으며 접근성 권한과 독립)
- URL별 Reuse Existing URL Window 토글. 활성화 후 해당 launchable이 처음 만든 --app 창 ID만
  현재 Chap/Chrome 세션 동안 기억해 재사용하며, 사용자 Chrome 탭은 검색하지 않는다.
- URL → HTTP(S) URL 검증 후 Chrome --app 모드 + 단일 request coordinator 직렬 실행 + AX readback 검증
- App → 실행 전 baseline 대비 첫 새 창 하나, 없으면 focused window 하나 + AX readback 검증
  (Office는 리사이즈 가능한 비표준 문서창과 시작창→문서창 전환을 추가 관찰)
- AX bounds 결과: position/size set error와 실제 readback을 반환하고 fully/partial/failed로 기록
  - partial/failed는 판정 근거(요청 대비 실제 position/size, 어느 축이 tolerance를 벗어났는지,
    AX 에러 코드)를 통합 로그와 CSV의 detail 열에 함께 남김
  - 리사이즈 대상 창을 못 찾고 끝나면 창 개수·focused 창 메타데이터를 detail 열에 기록
    (통합 로그 보존 기간이 짧아 며칠 뒤 원인 추적이 불가능해지는 것을 방지)
- URL/App AX 리사이즈 실패 시 권한 상태를 재확인하고, 권한이 빠진 경우 상태바 경고 + 1회 알림
- Settings 저장: 선택 항목이 아닌 전체 sites 배열의 필수값·HTTP(S) URL·크기·preset·중복 검증
- Settings 하단 탭: 고정 사이드바와 하단 도구막대는 유지하고 오른쪽 패널만 전환.
  Launchables는 실행 항목 편집, General은 Option 단축키·가이드·로그인 실행·상태바 아이콘
  설정을 제공하며 General에서 사이드바 항목을 선택하면 Launchables로 복귀
- Import: 안전 정규화 후 전체 validation, 차단 이슈 시 파일/VM 무변경, fixes/warnings 표시
  - 차단/실패 알림에 "Show Expected Format" 버튼: 필수 필드 설명 + 예제 JSON 표시 (Copy 가능)
  - 성공 시 일반 저장 경로를 사용해 Login Item 상태와 메뉴를 즉시 반영
- Legacy displayName: unique name만 UUID 보강; connected UUID는 displayName 보강/갱신;
  stale UUID 갱신, ambiguous/disconnected는 재선택 안내
- Settings/QA/Welcome 중 마지막 관리 창 종료 시 activation policy를 accessory로 복원
- 숫자 width/height는 draft로 편집해 Enter/blur 때 commit하며 실제 변경 때만 Custom 전환
- Follow Cursor 미니맵은 각 연결 화면의 화면별 size/default size preview를 동시에 표시한다. Follow Cursor에서 화면을 클릭하면 커서 추적을 유지한 채 그 화면을 size/preset 편집 대상으로 삼고, 일반 모드에서 클릭하면 해당 화면을 사이트 target으로 선택한다. 각 preview 창 중앙에 preset 또는 Custom label을 표시한다.
- Finder → 폴더 열기 + 리사이즈 (단일 AppleScript, 딜레이 없음)
- Shell → 스크립트 실행 (리사이즈 없음)
- 멀티 모니터 지원 + Display Picker로 고정 디스플레이 선택, Follow Cursor로 커서 화면 실행
- 윈도우 항상 대상 화면 중앙 배치 (centeredBounds 함수)
- 크기 프리셋: Compact, Focus, Standard, Comfortable, Wide, Tall, Workspace, Max, Custom
- Follow Cursor 디스플레이 프리셋은 내장 화면 기준 크기로 계산 후 커서 화면에 맞춤
- 화면별 size override: Follow Cursor에서만 적용한다. All Displays에서 편집 대상으로 고른 화면의 preset/custom size는 해당 화면 override로 저장되며, explicit display target 모드의 size edit는 site 전체 size를 갱신한다.
- 클릭 편집 + 자동 저장 (Enter/포커스 이동 시)
- 사이트별 커스텀 단축키 (optional, 정확히 한 글자, 중복 체크, 예약키 ./, 차단)
  - 단축키 정규화(sanitizedShortcuts): UI 저장뿐 아니라 config 로드(loadConfig)·Import
    경로에서도 다글자·중복(대소문자 무시, 앞의 것 유지)·예약키(./,)·공백을 정리하고,
    config 로드 중 바뀐 값은 즉시 저장. 손으로 편집한 ~/.chap.json이나 Import JSON의
    잘못된 단축키가 런타임이나 다음 실행에 새어 들지 않음
- 사이트 중복 체크 (동일 URL/앱/폴더 저장 차단)
- 필수 필드 미입력 시 저장 차단 (URL/앱경로/폴더/스크립트)
- 사이트 검색 (사이드바 이름 필터)
- 사이트 추가 시 Name 필드 자동 포커스 + 타입별 초기 추천 크기(URL Standard 상당, App Comfortable 상당, Finder Compact 상당)
- Import (파일/Paste JSON/드래그앤드랍) + Export → ~/Downloads
- ConfigStore가 config 읽기/쓰기/백업(.bak)/레거시 정리를 일원화; 파싱 실패 시 기본값 복구
- 레거시 필드 자동 정리 (x, y, hotkey, showGhostWindow, runInBackground)
- 타입별 그룹 사이드바 + 메뉴바 구분선
  - 검색 중이 아니면 url/app/finder/shell 네 섹션을 항상 표시하고, 빈 섹션은
    "Add <Type>" 행으로 해당 타입 항목을 바로 추가 (검색 중에는 매칭 없는 섹션 숨김)
- 드래그앤드랍 순서 변경 (같은 타입 내에서만)
- 방향키(↑↓) 목록 이동
- Q&A 페이지 (메뉴바에서 접근)
- 설정 창은 770x680 크기로 커서 화면 중앙에 표시
- Guide Window (리사이즈 위치 미리보기)
  - 토큰 기반 소유권: show가 토큰을 반환하고 dismiss(token)은 그 토큰이 현재일 때만 자기 창을 닫음.
    빠른 연속 실행 시 stale한 dismiss 완료 핸들러가 새 창을 죽여 유령 창이 남던 레이스를 방지
- 접근성 권한 안내 직후 자동 재시도 + 권한 제거 감지
- Launch at Login (SMAppService)
- 상태바 아이콘 선택 (Default/Lightning) — 메뉴바 Icon 서브메뉴에서 즉시 변경, config에 저장·재시작 유지
- Restart (메뉴바) / Restart App·Uninstall (설정 창 하단 folder 메뉴)

## 런처 타입별 동작

  URL:     HTTP(S) URL 검증 → Chrome --app 모드 실행 → AX API로 새 윈도우 감지 → position/size 설정
  App:     NSWorkspace.openApplication → AXObserver(kAXWindowCreated) → 리사이즈 가능 윈도우 중앙정렬
  Finder:  단일 AppleScript로 열기+리사이즈 동시 (딜레이 없음)
  Shell:   Process로 스크립트 실행 (리사이즈 없음)

리사이즈 전략:
  URL (Chrome 실행 중):  AX API 폴링 50ms 간격 (캐싱한 Chrome PID에서 새 윈도우 비교 감지, 최대 6초)
  URL (콜드 스타트):     AX API 폴링 100ms 간격 (최대 10초)
  App (실행 중):         AXObserver + 50ms 재스캔, 새 창이 없으면 0.2초 후 focused 창 하나 처리
  App (콜드 스타트):     AXObserver + 50ms 재스캔 (일반 최대 20초, Office 최대 30초),
                        focused fallback은 timeout 이후
  App (AXObserver 실패): 폴링 폴백 120ms 간격
  Finder:               딜레이 없음 (열기+리사이즈 단일 스크립트)

Chrome 윈도우 감지 방식:
  1. 모든 요청을 단일 requestCoordinator serial queue에서 처리
     (선택적 동일 URL 재사용 → cached Chrome PID baseline → open -na Process
     → 새 창 polling → AX readback 검증).
     이전 요청 완료 전 다음 Process를 시작하지 않아 빠른 연속 launch도 요청과 생성 창이
     1:1로 대응함. queue wait와 processing latency, baseline/launch/window wait/AX apply,
     PID 전환 경로를 분리해 로그에 기록
  2. reuseExistingWindow가 켜져 있으면 해당 launchable이 현재 Chap/Chrome 세션에서 직접 생성한
     Chrome window ID만 전면화한다. 첫 실행은 launch 전후 AppleScript window ID 차집합이 정확히
     하나일 때만 소유 창으로 등록한다. ID가 없거나 무효·모호하면 사용자 탭을 검색하지 않고 새 --app
     창을 열며, 재사용 창의 크기·위치는 그 ID에 직접 적용한다. 연결 상태는 Site UUID별로 URL,
     window ID, Chrome PID, process launch date를 메모리에만 보관하고 Chap 재시작 시 초기화한다.
     토글 비활성화·URL 변경·창 종료·Chrome 재시작 시 폐기하며, 탭 URL·제목·focused/frontmost
     window는 대상 판정이나 폴백에 사용하지 않는다. 상세 상태 전이는 FLOW.md §7.1.1 참조
  3. 실행 전 캐싱한 Chrome PID의 전체 윈도우 목록(AXUIElement[]) 저장
     - running 상태에서 AX 읽기가 순간적으로 빈 목록을 반환할 수 있어 최대 5회(30ms 간격)
       재시도해 스냅샷을 확보 (captureExistingWindows). 빈 스냅샷을 기준으로 삼으면 기존 창이
       새 창으로 오인돼 리사이즈되는(사용자 창이 튀는) 문제를 방지. 진짜 무창 Chrome은 빈 배열 유지
  4. 매 폴링에서 최신 live Chrome 프로세스를 조회. 동일 PID면 CFEqual 차집합, PID가 바뀌면
     실행 전 window fingerprint multiset을 차감해 복원 창과 요청 창을 구분
  5. ClaimedWindowRegistry가 이미 처리한 창의 재사용을 방어적으로 차단하고 닫힌 창은 pruning
  6. position/size 설정 후 실제 값을 읽어 tolerance 내 일치 여부를 fully/partial/failed로 기록
  7. 새 윈도우를 못 찾으면 타임아웃 (실패 로그)

App 윈도우 감지 방식 (AXObserver):
  1. openApplication 전 기존 AX window baseline을 캡처
  2. AXObserverCreate로 kAXWindowCreatedNotification 구독 + 50ms 재스캔
     (CFRunLoopRunInMode 0.05초 단위로 콜백 처리와 재스캔을 겸함)
  3. baseline에 없는 첫 표준 새 창 하나만 리사이즈 (기존 여러 창 일괄 변경 금지)
  4. Office 앱은 focused fallback/시작창 리사이즈 후에도 리사이즈 가능한 비표준 문서창과
     시작창→문서창 전환을 grace 동안 추가 관찰하고, 처리 완료한 창은 다시 적용하지 않음
  5. 실행 중 앱은 새 창이 0.2초 안에 없으면 focused 표준 창 하나를 즉시 처리;
     cold 앱은 timeout까지 새 창을 기다린 뒤 focused fallback
  6. AXWindow 역할과 position/size settable을 검증해 AXHelpTag 등 보조 요소를 제외
  7. AXObserver 생성 실패 시에도 Office 문서창 교체와 grace를 포함한 동일한 polling 정책 사용
  8. 각 적용 후 실제 position/size readback으로 fully/partial/failed 판정

리사이즈 CSV (DEBUG 전용):
  - ResizeLogger가 NSLock으로 디렉터리 생성, 헤더 확인/생성, append를 직렬화
  - size는 화면 fitting과 화면별 override를 반영해 AX에 실제 요청한 WxH
  - App total_time은 첫 fully/partial 적용 시점이며 failed 시도는 latency로 기록하지 않음
  - URL detail 끝에 단계별 timing key=value와 PID path를 추가해 Chrome 내부 지연을 분리

## 2026-08 현재 배포·AX 안정화 구조

### Full edition 배포

Chap의 전체 기능(URL/App 타 앱 창 제어와 Shell launcher)은 Mac App Store/TestFlight 대상이 아니다.
App Store 배포에는 App Sandbox가 필요하지만 AXUIElement 기반 타 앱 제어와 임의 Shell 실행은
sandbox 모델과 양립하지 않는다. 현재 Release source of truth는 `project.yml`이다.

```
Release
├── CODE_SIGN_STYLE = Manual
├── CODE_SIGN_IDENTITY = Developer ID Application
├── ENABLE_HARDENED_RUNTIME = YES
├── OTHER_CODE_SIGN_FLAGS = --timestamp
└── CODE_SIGN_ENTITLEMENTS = Sources/Chap/Chap.entitlements
    └── com.apple.security.automation.apple-events
```

`Chap.entitlements`에는 App Sandbox entitlement가 없다. `Scripts/build-release-dmg.sh`가
Developer ID signed universal archive를 검증해 DMG를 만들고,
`Scripts/notarize-release-dmg.sh`가 `notarytool submit --wait` → staple → signature/Gatekeeper
assessment를 수행한다. notarization credential은 keychain profile에만 저장하며 소스나 config에
넣지 않는다. Apple 절차는 https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution
를 따른다.

### 공용 AX bounds pipeline

`LauncherUtils.axApplyBounds(window:position:size:)`는 Chrome과 일반 App launcher가 공유하는
유일한 bounds 적용 종점이다. `AXResizePolicy.swift`는 AX 호출 없이 순수 계산·정책을 테스트한다.
[Rectangle](https://github.com/rxhanson/Rectangle)의 공개 구현에서 확인한 안정화 원칙을 다음처럼
적용한다.

```
AX app/window element 생성
├── AXUIElementSetMessagingTimeout(2s)
├── AXMinSize → AXMinimumSize를 순서대로 읽어 clamp 예측
├── app.AXEnhancedUserInterface == true이면 false로 전환
├── set size(target)
├── set position(target)
├── set size(target)                  // 다른 디스플레이 이동 뒤 재적용
├── 20ms 뒤 position/size readback
├── actual size가 tolerance(4pt)를 넘게 다르면
│   └── requested center를 보존한 position을 한 번 재적용 → readback
└── 원래 EnhancedUI가 true였을 때만 true로 복원
```

최종 `fully`/`partial`/`failed` 판정은 set 반환값이 아닌 readback 비교다. clamp가 일어나면
중앙 보정이 성공해도 size 자체는 요청값과 달라 `partial`로 남는다. `AXBoundsResult.notes`는
`enhancedUI=disabled`, `minSize=WxH`, `recentered=(x y)`를 CSV `detail`에 더한다.

`AXWindowIntrospection.swift`는 private `_AXUIElementGetWindow`를 사용하지 않는다. public
`CGWindowListCopyWindowInfo`에서 AX window의 `pid + frame`을 매칭해 session-local
`CGWindowID`를 얻고, 실패하면 top bit를 세운 `CFHash` 파생 id를 쓴다. 이 id는 적용·진단용이며
앱 relaunch 뒤에도 유지되는 식별자가 아니므로, Chrome relaunch 매칭은 계속
`title|role|subrole` fingerprint multiset이 담당한다.

### Accessibility prompt

`AccessibilityStateController.start()`는 테스트가 아닐 때 main run loop에서 한 번
`AXIsProcessTrustedWithOptions`를 요청한다. Welcome이 생략됐거나 `guideDisabled=true`여도
prompt가 유실되지 않는다. Welcome의 **Allow Accessibility** 버튼은 System Settings의
Accessibility pane을 여는 fallback이며, controller의 once-guard가 launch/Welcome 두 경로의
중복 prompt를 막는다. macOS는 이미 기록된 TCC 결정을 다시 표시하지 않을 수 있다.
